# 斗地主单挑残局解牌器 (Poker Endgame Solver)

给定一副**明牌**的单挑残局（双方手牌全公开、已知谁先手），判断**先手方是否存在必胜走法**，并给出第一手和完整推演。

> 起因：同学在群里发了一堆"唯一解"的恶心残局来挑战，说小程序要算一个小时。那就写个能算的。

## 项目背景与目标

### 面向谁、解决什么问题

斗地主残局（明牌、一对一）是常见的娱乐题目：两人手牌全部公开，轮流按规则出牌，先出完的人获胜。

这类题目有两个现实痛点：

1. **人算不动**：残局往往有几十张牌，分支数呈指数增长。网上小程序的实现常常要几十秒甚至几分钟。
2. **只说结论、不给理由**：很多工具只告诉你"有解 / 无解"，不告诉你**这一手为什么错**、**对手会怎么赢**。对想学习残局思路的人没有帮助。

本项目要解决的就是这两点：**尽可能快地给出确定结论**，并且**无论输赢都给出赢家的应对路线**。

### 已完成的功能

| 功能 | 说明 |
| :--- | :--- |
| 完整牌型引擎 | 单、对、三、三带一/二、顺子、连对、飞机（可带单/对）、四带二、四带两对、炸弹、王炸 |
| 穷尽搜索求解 | 布尔 negamax + 置换表 + 剪枝，结论是**确定**的（不是启发式猜测） |
| 并行加速 | 根候选分片，多线程独立置换表，找到解立即全局停止 |
| 命令行版本 | `dotnet run` 直接跑，无需安装 Unity |
| Unity 图形界面 | 点按输入、模拟对抗、实时显示耗时与节点数，可打包 Windows / Android |
| 模拟对抗 | 用户自己走出双方每一步；走错时**标出对方的制胜回应**，一步步演示到输 |

### 适用范围

- 一对一（单挑）残局，双方手牌全明。
- 支持"我方先手"与"对方先手"两种牌权。
- 支持自由拆牌（包括拆炸弹），程序只检查最终走法是否合法。

## 核心设计

### 1. 手牌的状态表示：位棋（Bitboard）

一手牌最多 15 种点数（3…2、小王、大王），每种最多 4 张。把每一张牌编码成 **4 bit**，整手牌压缩进一个 `ulong`：

```
点数索引： 0     1     2    ...   12    13     14
点数：     3     4     5    ...    2    小王   大王
bits：   [0-3] [4-7] [8-11] ... [48-51] [52-55] [56-59]
```

这样带来三个直接好处：

- **出一手牌 = 一次减法**：`剩余手牌 = 手牌 - 出的牌`。因为每个点数占 4 bit，4 张以内不会向高位借位，减法天然正确。
- **状态哈希只需三个 ulong**：双方手牌 + 台面牌型，`HashState` 里做几次乘法异或即可。
- **判空 / 比较是 O(1)**：`hand == 0` 就是出完。

**统计张数**用 SWAR 技巧一次折叠完 15 个字段，不循环：

```csharp
ulong x = hand;
x = (x & 0x0F0F0F0F0F0F0F0FUL) + ((x >> 4) & 0x0F0F0F0F0F0F0F0FUL);
// …再折叠两次，低 4 bit 就是总张数
```

走法排序里这个函数会被调用上千万次，SWAR 比逐点循环快一个数量级。

### 2. 搜索算法：布尔 negamax

我们**只关心胜负，不关心赢多少**，所以不用完整的 minimax 评分，而是用一个布尔函数：

```
Win(当前方手牌 me, 对方手牌 opp, 台面牌 prev) -> bool
「当前行动方能否先出完」
```

规则本身保证递归无环：每次递归要么某一方手牌减少，要么台面被清空（过牌）。所以可以放心做记忆化。

关键在于**「过」是独立分支**：

- 自由出牌时（台面为空）**必须出牌**；
- 面对别人的牌时可以**选择压**，也**可以选择过**。

很多实现会漏掉"过"这条分支，导致误判。本项目显式处理，并做了一次针对性修复（见 `ParallelSolver` 里 `rootMoves.Count == 0` 的分支）——**压不住不等于输，还可以过**。

### 3. 置换表：开放寻址 + 紧凑编码

同一局面会被不同路径反复到达，必须缓存。用 `Dictionary` 在千万级状态下内存会爆（每项几十字节），所以用**开放寻址哈希表**：

```
ulong  hash[2^N]     // 8 字节
ushort tag[2^N]      // 2 字节
byte   value[2^N]    // 1 字节：0=空 1=假 2=真
```

每条约 11 字节。装载率超过 80% 后停止插入（避免探测链过长），达到 50% 时扩容。

**为什么不用更大的表**：实测在 PC 上 2^26（约 700MB）时单节点开销反而上升——每次查表都是随机内存访问，大表几乎全部 cache miss，而小表能被 L2/L3 部分吸收。所以表大小是**可调参数**，按设备内存选择。

### 4. 启发式：MinHands（最少几手出完）

排序的关键指标：出一手牌后，剩余的牌**最少还要几手才能出完**。用两种贪心顺序各算一遍取小（先连对 / 先顺子），比单一贪心稳。

这个启发式让搜索优先走"看起来最快能走完"的分支，剪枝效果显著。

### 5. 剪枝

除了置换表命中，还有几条针对性剪枝：

| 剪枝 | 条件 | 效果 |
| :--- | :--- | :--- |
| 一手走完 | 出的牌 == 全部手牌 | 直接判胜 |
| 出完能清台 | 剩余 1 手，且对方压不住这手 | 直接判胜 |
| 过牌前瞻 | 对方一手就能走完 → 过牌必输，不递归 | 省一次完整搜索 |
| 超时/内存熔断 | 周期性检查 | 保证优雅停止，不崩溃 |

### 6. 并行策略

把**根节点的候选走法**分片，每个线程持有独立置换表和搜索器：

```
线程 t 负责候选 i  where  i % ThreadCount == t
找到「对方无法取胜」的候选 → Interlocked 标记全局停止
```

这样线程之间不需要锁，也不会重复搜索同一个候选。代价是置换表不共享，但实测收益大于损失。

**为什么不用动态任务队列**：也试过「谁先空谁取下一个候选」，结果在 20v14 上慢了近一倍
（16.24 秒 vs 8.19 秒，节点数 41M → 68M）。原因是候选已按希望大小排序，
静态分片能让**所有线程一开始就同时展开一个靠前的候选**；动态队列退化成从前往后串行抢任务，
还打散了每线程置换表的时间局部性。

**线程数为什么是 4**：在 12 逻辑核的机器上实测 4 / 6 / 8 / 12 线程，
越多越慢（8 线程 17.9 秒、12 线程 102 秒）——瓶颈是内存带宽，不是 CPU。

### 7. 残局定式库（EndgameBook）

**先说结论：网上不存在可用的斗地主残局定式表。**

查了几个公开实现（[Tim's Blog](https://wuzhiwei.net/doudizhu_solver/)、
[naturalleo/doudizhu_endgame](https://github.com/naturalleo/doudizhu_endgame)）
和一批攻略文章，它们全是「搜索求解」或「人类经验描述」，没有严格可验证的定式库。

原因是结构性的：

- 状态空间是 15 种点数 × 每点 0~4 张，完整预计算不可行；
- 同一个结构（如「三带二 + 单张」）在不同牌力下结论可能**相反**；
- 攻略里的「技巧」是启发式，不能当公式用。

**所以本项目只收录能严格证明的两条定式：**

| 定式 | 条件 | 结论 |
| :--- | :--- | :--- |
| **D1 一手清台** | 我方手牌本身是一个合法牌型 | 直接出完获胜 |
| **D2 残局锁** | 我方剩 1 手 + 对手压不住这一手 | 出这手后连着清台 |

命中时**跳过整棵搜索树**（0 节点、0 毫秒）。实测：`333 44` vs `55 66` 从 2 节点降到 0。

**另外提供「局面特征分析」**（不是结论，是帮人看懂局面）：

```
张数 14 vs 20　最少手数 6 vs 8
炸弹 0 vs 1　大牌(2/王) 3 vs 1
手数上我方明显占优，炸弹劣势，大牌更多
```

它回答的是「**为什么**赢/输」，比一句结论更有用。

### 8. 残局记忆库（EndgameMemory）

解过的残局会**自动记下来**，下次输入同一局面直接秒出。

**边界说明**：只做**完全相同局面**的精确匹配。相似局面绝不复用——
斗地主里差一张牌结论就可能相反，泛化就等于编答案。

- 存储：一个纯文本文件，一行一条，几十条只有几 KB
  （`persistentDataPath/endgame_memory.txt`）
- 求解成功后自动写入；超时/超内存的结果不记，避免污染
- 命中时显示「命中 N 次，首次 YYYY-MM-DD」
- 启动时状态栏显示「已记忆 X 个残局」

**这是「记忆」不是「泛化」**——它能让你重复测试同一批残局时越用越快，
但不会对没见过的局面做任何猜测。

### 9. 界面与算法分离

| 层 | 文件 | 依赖 |
| :--- | :--- | :--- |
| 算法核心 | `src/Core/` 五个文件（约 2000 行） | **只有 `System`** |
| 命令行 | `src/Cli/Program.cs` | .NET 8 |
| 图形界面 | `unity/`（见说明） | Unity 2022.3 |

**算法层零 Unity 依赖**，所以可以独立编译、独立测试、独立做实验——这也是本项目能把性能从 20 秒优化到 8 秒的原因：实验迭代不受引擎拖累。

## 复杂度与性能分析

### 理论复杂度

状态空间上界是双方手牌划分的组合数，呈指数级。实际搜索量靠三层手段压下来：

1. **置换表**：把重复子问题从"指数重复计算"降为 O(1) 查表。
2. **启发式排序**：先搜更可能成功的分支，命中后立即剪掉其余。
3. **剪枝**：一手走完、出完能清台等结构性判断，跳过整棵子树。

### 实测调优过程（几个有代表性的坑）

| 现象 | 原因 | 处理 | 收益 |
| :--- | :--- | :--- | :--- |
| 手数缓存用 `Dictionary`，重负载时速度从 5.4M 掉到 1.8M 节点/秒 | 千万级查询后哈希表扩容，重建整表 | 换成固定 2^17 的直接映射表（冲突覆盖，不影响正确性） | **2.5 倍** |
| 8 线程比 4 线程还慢 | 内存带宽饱和 + 8 份大置换表抢 cache | 保持 4 线程 | 避免负优化 |
| 单线程 5 秒必超时 | 大局面候选太多 | 根候选分片并行 | 可算 |
| 候选排序把真解排到第 18 位 | `MinHands` 是贪心上界，会低估大牌结构 | 根节点改用"对手压制代价"辅助排序 | 20 s → 8 s |
| 判"必败"时直接返回 | 漏了"过牌"这条合法分支 | 补 `rootMoves.Count == 0` 的过牌判定 | 修复误判 |
| 动态任务队列比静态分片慢一倍 | 打散了置换表的时间局部性；候选已排序，静态分片更能并行展开靠前候选 | 保留静态分片 | 16.2 s → 8.2 s |
| 置换表开 2^26 没有收益 | 排序改进后搜索量远小于表容量 | 降到 2^25（PC）/ 2^24（手机） | 省 2 倍内存，速度不变 |
| 把张数缓存在 Move 里 | 排序比较时的 SWAR 折叠看起来是热点，实测差异在噪声内 | **回退** | 无收益 |
| 置换表三数组合并成结构体数组 | 想让一次探测只碰一条 cache line，结果内存从 176MB 涨到 256MB/线程 | **回退（慢 2.4 倍）** | 负结果 |
| 排序时移动索引而不是结构体 | 想省掉 24 字节拷贝，但 `moves[idx[j]]` 的双重间接寻址更贵 | **回退（慢 2.5 倍）** | 负结果 |
| **置换表改 4 路分桶** | 探测长度从最多 64 降到固定 4，同桶条目内存连续 | **保留** | **20v14: 8.4 s → 6.4 s** |

### 设备自适应

| 设备 | 线程 | 置换表 | 内存上限 |
| :--- | :--- | :--- | :--- |
| PC | 4 | 2^25（约 335 MB/线程） | 2 GB |
| 手机 ≥6 GB RAM | 4 | 2^24 | 1.2 GB |
| 手机 4~6 GB | 4 | 2^23 | 900 MB |
| 手机 <4 GB | 2~3 | 2^22 | 600 MB |

**表大小怎么定的**：同一局面下 2^24 / 2^25 / 2^26 实测耗时 7.4 / 7.6 / 7.6 秒、节点数完全一致。
说明改进排序后搜索量远小于表容量，**再大的表只是浪费内存**，所以统一降了一档。

**移动端为什么必须用 IL2CPP + ARM64**：算法核心全是 `ulong` 位运算。ARMv7 是 32 位架构，64 位整数要靠多条指令软件模拟，再叠加 Mono JIT 的解释开销，实测**同一局面慢 15~20 倍**。换成 IL2CPP + ARM64 后回到正常水平。

## 已知局限

1. **只支持一对一残局**，不支持三人斗地主（地主 vs 两个农民需要额外的配合逻辑）。
2. **必须是明牌**，不支持记牌 / 概率推断。
3. **极端局面仍可能超时**：例如双方各 17 张且高度零散的随机局面，搜索空间极大。程序会明确返回"未完成"，而不是给错误结论。
4. **并行置换表不共享**：每个线程独立，有重复计算，换来的是无锁。
5. **排序是启发式**：对某些残局（如"顺子开局"类）真解仍可能排在中后段，导致耗时高于理论最优。
6. **没做残局公式库**：常见的定式残局（如"双王 + 单张"必胜）仍靠搜索，没有走查表捷径。
